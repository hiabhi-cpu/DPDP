Design principle: thin middleware, immutable audit, zero clinical data

Your Go backend is a consent event bus — it receives triggers from HMS, issues consent decisions, and writes immutable audit records. It never proxies clinical data. Every layer is stateless and horizontally scalable from Day 1.

Go is an excellent choice for this system

Go's concurrency model handles high-throughput consent checks perfectly — hospitals may have 200+ OPD patients per hour. Goroutines make the audit logging async without blocking the consent check response. Strong typing reduces bugs in compliance-critical code.

Go library recommendations — every layer
HTTP Framework
Gin Recommended
Fastest Go HTTP framework. Excellent middleware support for auth, logging, rate limiting. Huge community. gin-gonic/gin on GitHub.
Database ORM
GORM Recommended
Full-featured ORM for PostgreSQL. Auto-migrations, associations, hooks. Use gorm.io/gorm + gorm.io/driver/postgres. For audit log: use raw sqlx for append-only inserts — more control.
Raw SQL (audit)
sqlx For audit log only
jmoiron/sqlx gives you raw SQL with struct scanning. Use this for the append-only audit table — you want explicit control over inserts, no accidental updates via ORM.
JWT Auth
golang-jwt/jwt
Standard JWT library for Go. Use RS256 (RSA) not HS256 — asymmetric signing means each microservice can verify tokens without sharing the signing secret.
Redis client
go-redis/redis v9
Official Redis client for Go. Use for session store, job queue (consent PDF generation), and rate limiting buckets. Supports Redis Streams for event pub/sub between services.
Hashing / Crypto
crypto/sha256 (stdlib)
Go standard library. No external dependency needed. Use crypto/sha256 for consent payload hashing, crypto/rand for secure token generation, crypto/aes for field-level encryption.
HTTP client (HMS)
resty / stdlib net/http
go-resty/resty for outbound calls to HMS APIs — retry logic, timeout config, mTLS support built in. Use for Practo and MocDoc API calls.
HL7 FHIR R4
google/fhir (Go) Complex
google/fhir has a Go library for FHIR R4 models. Alternatively, use samply/blaze or build FHIR JSON manually — ABDM uses a subset of FHIR that's not huge. Start with manual JSON, add library later.
PDF generation
jung-kurt/gofpdf or go-wkhtmltopdf
For consent PDF receipts and monthly reports. gofpdf is pure Go (no external deps). go-wkhtmltopdf renders HTML to PDF — easier for complex report layouts.
Config management
viper + godotenv
spf13/viper for multi-source config (env vars, YAML, AWS Secrets Manager). Never hardcode DB passwords or API keys — use env vars from Day 1.
Logging
uber-go/zap Recommended
Structured JSON logging. Fast, zero-allocation. Every consent event must be logged with requestId, hospitalId, patientId (hashed), timestamp, and outcome. Structured logs = queryable audit trail.
Testing
testify + gomock
stretchr/testify for assertions. golang/mock for service mocking. Consent logic is compliance-critical — 80%+ test coverage is non-negotiable. Wrong consent decisions are legal liability.
AWS SDK
aws-sdk-go-v2
Official AWS SDK v2 for Go. Use for S3 (consent PDFs), SES (emails), RDS (IAM auth), Secrets Manager (API keys). Always use IAM roles — never hardcode AWS credentials.

On "Golang frontend library" — honest answer

Practical recommendation: React for dashboard + Templ for HMS embeddable widget

Use React + TypeScript for the hospital admin dashboard and patient portal — complex charts, tables, and real-time updates need React's ecosystem. Use Templ + HTMX for the embeddable JS widget that sits inside the HMS screens — it's lightweight, server-rendered, and drops into any HMS page with a single script tag. React Native for the tablet kiosk. Your Go backend serves all three via REST APIs.

Critical things to get right from Day 1
Multi-tenancy from the first line of code
Every DB table must have a hospital_id column. Every API must scope queries by hospital_id from the JWT. Never let Hospital A see Hospital B's data. This is the hardest thing to retrofit — build it day one.
Audit log is append-only — no UPDATE, no DELETE ever
Use PostgreSQL row-level security to block UPDATE and DELETE on the audit_log table at the DB level — not just application level. Even your own backend cannot tamper with it. This is your legal evidence.
Consent check API must respond under 300ms
HMS calls your API before rendering a patient record. If you're slow, doctors get frustrated and hospitals switch off the integration. Cache consent status in Redis with a 5-minute TTL. Cold path hits PostgreSQL, warm path hits Redis.
Patient ID must be hashed in your DB — never store raw ABHA/phone
Store HMAC-SHA256(patientPhone + hospitalSalt) as the patient identifier in your consent vault. Even if your DB is breached, patient identities are not exposed. The hospital provides the salt — you never know the raw patient identity.
AWS Mumbai region only — data localization is a DPDP requirement
All RDS instances, S3 buckets, and Elasticache clusters must be in ap-south-1 (Mumbai). Set an AWS SCP (Service Control Policy) on your account to block any resource creation outside India. One wrong region = DPDP violation.
Idempotent consent API — duplicate submissions must be safe
A tablet kiosk on flaky hospital WiFi may submit consent twice. Use an idempotency key (consentRequestId) on every POST /consent. Store processed keys in Redis for 24 hours. Duplicate submission returns the original consent record, not a new one.
Graceful offline mode for tablet kiosk
Hospital internet goes down. The kiosk must queue consent records locally (SQLite on device) and sync when connectivity returns. A hospital cannot stop OPD because your backend is unreachable. Offline-first design is non-negotiable for India.
Rate limit per hospital API key — not per IP
A hospital with 300 OPD patients/day might burst 50 requests/minute legitimately. Rate limit by hospital_id + endpoint, not by IP. Use token bucket algorithm in Redis. Alert if a hospital suddenly hits 10x their normal rate — possible integration bug or abuse.

The one thing that will kill you if you get it wrong

Multi-tenancy isolation. If a bug causes Hospital A's patients to appear in Hospital B's dashboard — even for 5 minutes — you lose both customers, face potential DPDP liability, and your reputation is finished. Write a dedicated integration test suite that verifies tenant isolation for every single API endpoint before any release.
